# GenAI 기초: LLM 기반 업무 자동화 — 교육생 문의 답변 초안 작성기

교육 운영팀이 매일 받는 교육생 문의(출석·훈련장려금·중도 하차·장비 대여)에 대해, LLM이 **운영규정 근거가 붙은 답변 초안**을 만들도록 설계하고 검증한 결과물이다.
3종 모델을 같은 입력으로 비교해 모델을 고르고, 시스템 프롬프트를 v1 → v2로 개선하고, 환각 검증과 12턴 대화로 동작을 확인했다.

> 규정은 과제용으로 만든 **가상의 규정**(`prompts/regulation_sample.md`)이며, 교육생 이름은 모두 OO로 가렸다.

## 한눈에 보기

| 항목 | 내용 |
|---|---|
| 업무 과업 | 교육생 문의 → 규정 근거 답변 초안 (출력: 답변 초안 / 근거 규정 / 확인 필요 항목) |
| 타겟 사용자 | 교육 운영 매니저 (문의 1차 응대 담당) |
| 비교 모델 | Claude Haiku / Sonnet / Opus (같은 프롬프트, 같은 입력 3종 × 3모델 = 9회 실행) |
| 선정 모델 | **Claude Opus** (가중 합계 52/55) — 정확성·확인 필요 항목 질 만점 |
| 프롬프트 | v1(한 줄) → v2(근거 원칙 + 되묻기 + 3단 출력 + Few-shot 3개) |
| 환각 검증 | 7문항, Pass 7 (A 3 / B 4), Fail 0. 대조군 v1은 3문항 모두 Fail |
| 대화 로그 | 12턴 (채널·톤 변경, 추가 정보, 규정 개정, 환각 유도, 문맥 회상 포함) |
| 보너스 | 답변 자동 점검 스크립트 `bonus/check_output.py` |

## 평가 항목별 위치

| 평가 항목 | 확인 위치 |
|---|---|
| **1-1** 업무 과업 1개 정의 (타겟 사용자/입력/출력 규격) | `01` 1장 |
| **1-2** 복사해 쓰는 입력 템플릿 | `01` 3장, `prompts/input_template.md` |
| **1-3** 3종 이상 모델 비교 표 (평가 축 4개 이상 + 점수 + 근거) | `02` 4장 (평가 축 7개, 가중 점수, 축별 근거) |
| **1-4** Few-shot 3개, 1개는 모호한 입력 → 되묻기 | `01` 6장 (예시 2), 실제 동작은 `02` 3.3 |
| **1-5** 환각 검증 질문 5개 이상 + Pass/Fail | `03` 3장 (7문항) |
| **1-6** 10턴 이상 대화 + 중간 조건 변경 반영 | `04` (12턴, 조건 변경 4회) |
| **2-1** 시스템 프롬프트 / 유저 프롬프트 / 입력 템플릿 분리 | `01` 2장 (분리 표), `prompts/` |
| **2-2** 프롬프트 v1 → v2 개선 과정 | `01` 5장, 7장 (실제 출력 비교) |
| **2-3** 평가 축 기반 구조화된 모델 비교 | `02` 4.1 (축 정의·5점 기준·가중치) |
| **3-1** 환각 = 사실 오류, 창의적 생성과 구분 이유 | `03` 1장, `05` Q1 |
| **3-2** Pass A/B, Fail 판정 방법 | `03` 2장, `05` Q2 |
| **3-3** 모델 선정 이유와 과업 특성 연결 | `02` 5장, `05` Q3 |
| **4-1** 무료 모델만 쓸 때 품질 유지 | `05` Q4 |
| **4-2** 정책이 자주 바뀔 때 환각 감소 운영 전략 | `05` Q5 |
| **4-3** 10턴 이상 문맥 끊김 대응 프롬프트 구조 | `05` Q6 |
| **5** 보너스 | `bonus/check_output.py` (아래) |

## 보너스: 답변 자동 점검 스크립트

LLM 답변이 ① 3단 구성 또는 [되묻기] 형식을 지켰는지 ② 근거 자료(규정 + 교육생 정보)에 없는 **조항 번호**를 근거로 썼는지 ③ 근거 자료에 없는 **금액·비율**을 만들었는지를 규칙으로 점검한다. 출석률처럼 근거 자료의 일수로 계산할 수 있는 비율은 허용한다. 담당자가 보기 전에 거르는 1차 필터다.

```bash
python3 bonus/check_output.py <근거자료 파일> <답변.md> [<답변.md> ...]
```

이 저장소의 실험 결과에 돌린 결과:

| 대상 | 결과 |
|---|---|
| 모델 비교 9건 (v2) | 9/9 OK |
| 환각 검증 7건 (v2, Opus) | 7/7 OK |
| v1 대조군 3건 | 3/3 WARN — 형식 누락 3건, H2에서 근거 없는 비율 `3.3%`, `8.8%`, `22%` 검출 |

한계: 규칙 기반이라 "문장으로 된 틀린 사실"(예: 없는 서류 이름)은 잡지 못한다. 그래서 사람의 최종 검토를 대체하지 않는다.

## 실행 방법과 한계

- 실행 환경: Claude Code 서브에이전트 (`model: haiku / sonnet / opus`). 각 모델에게 시스템 프롬프트 파일과 유저 입력 파일을 읽게 하고 그 응답 원문을 `raw_outputs/`에 그대로 저장했다.
- API 키가 없는 환경이라 타사 모델(GPT, Gemini)은 비교하지 못했다. 같은 입력과 평가표를 그대로 쓰면 추가할 수 있다.
- 각 입력은 1회씩 실행했다. 반복 실행에 따른 출력 편차는 측정하지 않았다.

## 배운 점

- 같은 모델이라도 **규정 원문 제공 + 근거 원칙 + 확인 필요 출력란**만으로 환각 Fail 3건이 Pass로 바뀌었다. 모델 교체보다 근거를 주는 구조가 먼저다.
- 모델 비교의 차이는 "답이 맞았는가"보다 **"확인 필요 항목이 담당자에게 도움이 되는가"** 에서 크게 났다. 초안 자동화에서는 검토 포인트의 질이 생산성을 정한다.
- 10턴이 넘는 대화에서는 강한 모델도 앞에서 정한 형식 조건(3문장 이내)을 한 번 놓쳤다. 조건을 대화 기록에 맡기지 말고 매 턴 상태 블록으로 다시 넣어야 한다.
